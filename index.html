Nossa História

A Butcha Brigadeiros nasceu como um audacioso projeto que transcendeu as paredes de sala de aula. O que começou como um incentivo ao empreendedorismo através do inovador Projeto Food Makers, rapidamente floresceu em uma marca de dar sabor e propósito à comunidade.

Nosso propósito vai muito além de produzir doces finos. Nós queremos apresentar uma autêntica experiência de valorização da cultura e culinária, usando insumos de altíssima qualidade. Tudo isso sempre feito pelas apaixonadas mãos de jovens empreendedores focados num belo futuro, com o suporte contínuo da rede Calábria.

Guia do Estudante

Bem-vindo ao laboratório prático! Use este painel para explorar as vulnerabilidades descritas em "Protegendo Seus Aplicativos". Copie os códigos de teste (payloads) abaixo e execute-os na página.

PDF pág 3

1. Injeção de SQL (SQL Injection)

O que é: Modificar a consulta SQL original injetando comandos no banco de dados.

Como testar:

  1. Alterne o app para o modo Vulnerável.
  2. Vá para a seção "Rastrear Entrega do Pedido" na página.
  3. Insira um dos códigos abaixo no campo e clique em buscar:
' OR '1'='1
' UNION SELECT 'Invasor', 'SenhaHashAdmin123', 'admin@butcha.com.br' --

O que acontece: No modo vulnerável, a consulta retorna todos os pedidos (tautologia) ou revela o banco de credenciais administrativas. Mude para o modo Seguro e refaça a busca para ver como a parametrização neutraliza a ameaça.

gavel Prática Recomendada:

Nunca concatene parâmetros diretamente nas strings SQL. Use Prepared Statements (Consultas Parametrizadas) para validar os dados e separar a lógica do código SQL:

// Vulnerável (Concatenação):

`SELECT * FROM pedidos WHERE codigo_rastreio = '${val}'`

// Seguro (Prepared Statement):

`SELECT * FROM pedidos WHERE codigo_rastreio = ?`

PDF pág 4

2. Roubo por Scripts (XSS)

O que é: Inserir scripts na página que executam no navegador de quem a acessa.

Como testar:

  1. No modo Vulnerável, vá na seção "Mural de Depoimentos".
  2. Insira o payload abaixo na caixa de comentário e clique em publicar:
<img src="x" onerror="window.dispararAlertaXSS()">

O que acontece: O navegador renderiza o HTML diretamente via `innerHTML`, forçando a execução do script no evento de erro da imagem simulada. Isso abre a simulação de roubo de cookies. Alterne para o modo Seguro para ver como o escape de HTML anula a execução.

gavel Prática Recomendada:

Filtre e escape qualquer entrada de usuário antes de renderizá-la. No Frontend, prefira usar propriedades seguras que tratam os dados como texto puro:

// Vulnerável (Interpreta HTML/JS):

`elemento.innerHTML = inputUsuario;`

// Seguro (Trata apenas como texto):

`elemento.textContent = inputUsuario;`

PDF pág 5

3. Falsificação de Requisição (CSRF)

O que é: Enganar o usuário logado para executar ações indesejadas em outro site.

Como testar:

  1. Role até a seção "Simulador de Ataque CSRF".
  2. Verifique se o usuário possui 150 pontos na "Sessão Ativa".
  3. No anúncio malicioso flutuante que surgiu na tela ao rolar a página, clique em "REIVINDICAR MEUS BRIGADEIROS AGORA!".

O que acontece: No modo Vulnerável, a chamada POST secreta funciona, roubando os pontos do usuário. No modo Seguro, a requisição é bloqueada pois o servidor exige e valida um token anti-CSRF exclusivo da página principal.

gavel Prática Recomendada:

Exija Tokens Anti-CSRF em requisições que alteram estado (POST/PUT) e configure cookies com diretivas restritivas para evitar envio automático por sites terceiros:

// Cabeçalho HTTP com Token Anti-CSRF:

`X-CSRF-Token: token_gerado_no_backend`

// Cookies de Sessão protegidos:

`Set-Cookie: session=...; SameSite=Strict; Secure`
